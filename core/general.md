# 通用软件工程原则

本文档定义了 Vibe Coding 体系下不可动摇的代码质量标准。Agent 生成的任何代码都必须通过这些原则的审查。

## 核心设计哲学 (SOLID)

所有类和模块的设计必须遵循 SOLID 原则。

### 单一职责原则 (SRP)

- 一个类或模块应该只有一个改变的理由。
- 避免创建“上帝类” (God Class)。如果一个类既处理数据库连接又处理业务逻辑，必须拆分。

### 开闭原则 (OCP)

- 软件实体应该对扩展开放，对修改关闭。
- 通过接口 (Interface) 或抽象类 (Abstract Class) 来实现行为的变化，而不是通过修改现有的 `if-else` 逻辑。

### 里氏替换原则 (LSP)

- 子类对象必须能够替换掉所有父类对象，而不会导致程序错误。
- 子类不应抛出父类未声明的异常，也不应改变父类方法的预置条件。

### 接口隔离原则 (ISP)

- 不应强迫客户端依赖于它们不使用的方法。
- 将庞大的接口拆分为更小、更具体的接口。

### 依赖倒置原则 (DIP)

- 高层模块不应依赖低层模块，二者都应依赖其抽象。
- 抽象不应依赖细节，细节应依赖抽象。
- 在代码中通过依赖注入 (Dependency Injection) 来实现这一点。

## 代码整洁之道 (Clean Code)

### 命名规范

- **名副其实**：变量名必须清楚地表明它是做什么的。避免使用 `d`, `t`, `temp` 等无意义名称。
- **使用读得出来的名称**：避免缩写，除非是业界通用的 (如 `id`, `url`, `api`)。
- **类名**：使用名词或名词短语 (如 `Customer`, `Account`)。
- **方法名**：使用动词或动词短语 (如 `postPayment`, `deletePage`)。

### 函数设计

- **短小**：函数的长度应控制在屏幕可视范围内。
- **只做一件事**：一个函数应该只完成一个具体的任务。
- **参数数量**：理想的参数数量是零个。尽量避免三个以上的参数。如果参数过多，考虑将其封装为参数对象 (Parameter Object)。

### 注释原则

- **代码即文档**：尽量通过清晰的命名和结构来表达意图，而不是依赖注释。
- **避免废话注释**：不要为 Getter/Setter 或显而易见的代码写注释。
- **必要的注释**：仅用于解释“为什么这么做” (Why)，而不是“在做什么” (What)。对于复杂的算法或非直观的业务逻辑，必须添加注释。

## 现代化工程实践

### DRY (Don't Repeat Yourself)

- 系统中的每一项知识都必须具有单一、无歧义、权威的表示。
- 如果发现代码重复，提取为公共函数或基类。

### KISS (Keep It Simple, Stupid)

- 避免过度设计。在满足需求的前提下，选择最简单的实现方案。
- 不要为了炫技而使用复杂的语法特性。

### YAGNI (You Ain't Gonna Need It)

- 不要去实现目前不需要的功能。
- 只解决当下的问题，不要预想未来的需求而引入不必要的复杂度。

## 错误处理

### 使用异常而非返回码

- 在面向对象语言中，使用异常 (Exceptions) 来处理错误，而不是返回错误码。
- 异常处理代码应与业务逻辑分离。

### 定义特定领域的异常

- 不要抛出通用的 `Exception` 或 `Error`。
- 创建自定义异常类 (如 `UserNotFoundError`, `PaymentProcessingError`)，以便上层调用者能针对性地捕获和处理。

### 快速失败 (Fail Fast)

- 在方法的开头进行参数校验。如果参数无效，立即抛出异常，不要让错误的数据在系统中传递。
