# 测试标准与 TDD 工作流

本文档定义了 Vibe Coding 体系下的全方位测试策略。Agent 在编写代码时，必须同时满足流程要求（TDD）和质量要求（覆盖率与边界分析）。

## TDD 核心工作流 (The Process)

严格遵循红-绿-重构 (Red-Green-Refactor) 循环：

### 阶段一：红 (Red) - 编写失败测试

- **目标**：描述期望的行为。
- **行动**：
  - 创建一个新的测试函数。
  - 调用尚未实现的接口或方法。
  - 断言期望的返回值或状态变化。
- **验证**：运行测试，确认它失败了，并且失败的原因符合预期 (例如 `ImportError` 或 `AssertionError`)。

### 阶段二：绿 (Green) - 让测试通过

- **目标**：以最快速度让测试通过。
- **行动**：
  - 编写生产代码。
  - 在此阶段，允许使用“罪恶”的代码 (如硬编码返回值、复制粘贴)，只要能让测试通过即可。
  - 不要在此阶段进行优化或过度设计。
- **验证**：运行测试，确认变为绿色 (Pass)。

### 阶段三：重构 (Refactor) - 优化代码

- **目标**：消除重复，提高可读性，改善架构。
- **行动**：
  - 在测试通过的保护下，修改代码结构。
  - 提取方法，重命名变量，消除魔术数。
  - 应用设计模式。
- **验证**：每次修改后，必须立即运行测试，确保没有破坏现有功能。

## 测试用例设计策略 (Case Design)

Agent 在设计测试用例时，严禁只覆盖“快乐路径” (Happy Path)。必须通过以下维度进行全面分析：

### 边界条件分析 (Boundary Analysis)

检查输入参数的极限情况：

- **空值与零值**：`None`, `null`, `0`, `""`, `[]`, `{}`。
- **极值**：最大整数 (MaxInt), 最小整数 (MinInt), 极长字符串。
- **集合边界**：列表的第一个元素、最后一个元素、越界索引。
- **时间边界**：闰年、跨天、跨时区、超时。

### 错误与异常处理 (Error Handling)

验证代码能否正确处理非法输入：

- **非法参数**：传入错误的类型或格式。
- **外部依赖失败**：模拟 (Mock) 网络超时、数据库连接失败、文件权限拒绝。
- **断言异常**：使用 `pytest.raises` (或对应语言工具) 验证特定异常是否被抛出。

### 回归测试 (Regression Testing)

- **Bug 即测试**：每当修复一个 Bug 时，**必须**先编写一个复现该 Bug 的测试用例。
- **持久化**：该测试用例将永久存在于测试套件中，防止 Bug 再次出现。

## 测试覆盖率要求 (Code Coverage)

覆盖率是衡量测试完整性的客观指标。

### 覆盖率目标

- **行覆盖率 (Line Coverage)**：核心业务逻辑模块必须达到 **90%** 以上。
- **分支覆盖率 (Branch Coverage)**：重点关注 `if-else`, `switch-case` 的所有分支路径是否都被执行。

### 覆盖率约束

- 如果新增代码导致整体覆盖率下降，CI 构建将被标记为失败。
- 严禁为了刷覆盖率而编写没有断言 (Assertion) 的测试。

## 测试分层金字塔 (Testing Pyramid)

根据测试的粒度和运行速度进行分层：

### 单元测试 (Unit Tests)

- **范围**：独立的函数、类或模块。
- **特点**：极快 (毫秒级)、无外部依赖 (Mock 数据库和网络)。
- **比例**：占测试总量的 70-80%。
- **工具**：`pytest`, `unittest`, `gtest`, `junit`。

### 集成测试 (Integration Tests)

- **范围**：模块之间的交互、数据库交互、API 端点。
- **特点**：较慢、使用真实或容器化的数据库 (如 Testcontainers)。
- **比例**：占测试总量的 10-20%。
- **标记**：在代码中应明确标记 (如 `@pytest.mark.integration`)，以便在快速开发时可以选择性跳过。

### 端到端测试 (E2E Tests)

- **范围**：模拟用户真实操作流程。
- **特点**：最慢、易碎。
- **比例**：占测试总量的 5-10%。

## 测试代码质量 (Test Code Quality)

测试代码也是生产代码的一部分，必须遵守 Clean Code 原则。

### FIRST 原则

- **Fast (快速)**：测试应该运行得非常快。如果测试慢，开发者就不会频繁运行它们。
- **Independent (独立)**：测试之间不应相互依赖。严禁测试用例之间共享可变状态 (Global State)。每个测试运行前后的环境必须是一致的。
- **Repeatable (可重复)**：测试应在任何环境 (开发机、CI、生产环境) 下都能产生相同的结果。不要依赖网络或系统时间，使用 Mock/Stub。
- **Self-Validating (自验证)**：测试应该输出布尔值结果 (Pass/Fail)，不需要人工检查日志。
- **Timely (及时)**：测试应恰好在生产代码之前编写。

### AAA 模式

所有测试函数体应清晰地分为三个部分：

- **Arrange**：准备数据和环境。
- **Act**：调用被测方法。
- **Assert**：验证结果。

### 编写守则

- **避免逻辑**：测试代码中不应包含复杂的 `if-else` 或循环逻辑。测试应该尽可能是线性的。
- **断言聚焦**：每个测试应尽量只验证一个概念。

### 命名规范

测试函数的命名应清晰描述被测场景和预期结果。

- **推荐格式**：`test_方法名_场景_预期行为`
- **示例**：`test_calculate_total_with_empty_cart_returns_zero`

## 常见反模式 (Anti-Patterns)

- **测试代码未维护**：测试代码也是一等公民，必须像生产代码一样维护和重构。
- **过度 Mock**：如果测试中 Mock 了太多内部实现细节，会导致重构困难。测试应关注行为 (Behavior)，而非实现 (Implementation)。
- **断言过多**：每个测试应尽量只验证一个概念。
