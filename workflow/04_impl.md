# 编码实现工作流

本文档定义了 Vibe Coding 体系下的代码实现标准。Agent 必须严格执行 TDD 循环，并确保生成的代码符合架构设计。

## 前置检查 (Pre-flight Check)

在编写任何一行代码之前，Agent 必须确认：

- **需求明确**：已阅读 `01_analysis.md` 产出的需求文档。
- **设计就绪**：已阅读 `02_design.md` 产出的接口定义和类图。
- **环境正常**：已执行 `00_init.md`，且 CI/CD 流水线（如果有）处于绿色状态。

## 标准执行流程 (The Loop)

### 步骤一：生成测试脚手架

- 根据设计文档中的接口定义，在 `tests/` 目录下创建对应的测试文件。
- 引入被测模块（即使该模块尚未创建，也可以先写 import，允许 IDE 报错）。

### 步骤二：红 (Red) - 编写失败测试

- 选择一个最小的功能点（Unit）。
- 编写测试用例，断言预期的行为。
- **执行测试命令**（调用 Stack 文档中的指令，如 `uv run pytest`）。
- **验证失败**：确认测试失败的原因是 `ImportError` 或 `AssertionError`，而非语法错误。

### 步骤三：绿 (Green) - 最小实现

- 在 `src/` 目录下创建或修改源文件。
- 编写最简单的代码以通过测试。
  - 允许硬编码 (Hardcoding)。
  - 允许暂时忽略代码风格（Linter warnings）。
- **执行测试命令**。
- **验证通过**：确保测试变绿。

### 步骤四：重构 (Refactor) - 消除技术债务

- 在测试通过的保护下优化代码。
  - 消除重复代码 (DRY)。
  - 优化变量命名 (Clean Code)。
  - 添加类型注解 (Type Hints)。
  - 补充文档字符串 (Docstrings)。
- **执行 Linter**（调用 Stack 文档中的指令，如 `uv run ruff check`）。
- **再次执行测试**：确保重构没有破坏功能。

### 步骤五：原子提交 (Atomic Commit)

- 每完成一个上述循环（即一个功能点的 Red-Green-Refactor），必须根据 `core/git_flow.md` 的规范执行一次 Git 提交。

## 调试与自我修正协议

当代码无法按预期工作时，Agent 必须遵循以下调试逻辑，严禁盲目试错。

### 调试循环

- **分析报错**：仔细阅读 Traceback 或错误日志。不要只看最后一行。
- **定位根因**：
  - 是测试写错了？
  - 是逻辑实现错了？
  - 是环境配置问题？
- **提出假设**：在思考过程 (Chain of Thought) 中明确写出：“我怀疑是因为 X 导致了 Y”。
- **验证修复**：修改代码后，只运行失败的那个测试用例（使用 `-k` 参数或类似机制），以节省时间。

### 止损机制

- 如果连续 **3次** 尝试修复失败，Agent 必须停止修改代码。
- **回滚**：执行 `git reset --hard` 回退到上一个绿色的状态。
- **求助**：向用户输出详细的错误分析报告，并请求人工介入或提供更多上下文。

## 实现完成标准 (Definition of Done)

一个功能模块被视为“完成”，必须满足以下所有条件：

- **功能完整**：满足所有验收标准 (AC)。
- **测试通过**：所有单元测试和集成测试通过 (Pass)。
- **覆盖率达标**：核心逻辑覆盖率 > 90% (参考 `core/testing_standard.md` 的要求)。
- **静态检查通过**：没有 Linter 错误或 Type Checker 报错。
- **文档同步**：代码中的 Docstrings 已更新，且与 Mermaid 设计图保持一致。

## Agent 交互协议

### 代码输出规范

- **完整性**：在输出代码时，尽量提供完整的文件内容，或者提供带有明确上下文（行号或锚点）的 Diff。避免只输出孤立的代码片段。
- **文件路径**：代码块上方必须注释该文件的相对路径（如 `# src/services/user_service.py`）。

### 进度汇报

- 每完成一个大的功能块（Feature），更新 `03_progress.md` 中定义的进度追踪文件。
