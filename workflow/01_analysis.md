# 需求分析与决策工作流

本文档定义了 Vibe Coding 体系下的需求工程标准。在进入代码设计之前，Agent 必须扮演“产品经理”和“技术负责人”的角色，确保构建正确的产品。

## 核心原则：三思而后行 (Think Before Act)

- **拒绝模糊**：严禁基于模糊的指令（如“做一个更好看的登录页”）开始编码。必须通过提问将模糊需求转化为具体指标。
- **决策留痕**：所有的关键技术决策（选型、妥协、架构变更）必须记录在案，形成“决策记忆”。
- **验收前置**：在写代码之前，必须先定义“怎么才算做完了”（Definition of Done）。

## 标准执行步骤

### 步骤一：需求澄清 (Clarification Loop)

Agent 必须主动向用户提问，直到获得足够的信息来构建以下内容：

- **用户故事 (User Stories)**
  - 格式：`作为 <角色>，我想要 <功能>，以便于 <价值>`。
  - 示例：作为管理员，我想要批量导出用户数据，以便于进行月度统计。

- **验收标准 (Acceptance Criteria - AC)**
  - 这是 TDD 的基础。AC 必须是可测试的 (Testable)。
  - **Bad**: 登录速度要快。
  - **Good**: 在 4G 网络下，点击登录按钮后 1 秒内应渲染出首页，且 API 响应时间小于 200ms。

- **边界与限制 (Constraints)**
  - 识别非功能性需求（性能、安全性、兼容性）。
  - 明确“不做什​​么”（Out of Scope）。

### 步骤二：技术决策记录 (ADR - Architecture Decision Records)

当面临重要技术选择或架构变更时，Agent 必须生成轻量级的 ADR 记录。

- **何时记录**：
  - 选择数据库或关键库时（例如：为什么选 PostgreSQL 而不是 MongoDB？）。
  - 决定核心架构模式时（例如：为什么用同步 API 而不是消息队列？）。
- **记录格式**：
  - **背景**：面临的问题。
  - **选项**：考虑了哪些方案。
  - **决策**：最终选择了什么。
  - **后果**：这个选择带来的好处和潜在代价（技术债务）。

### 步骤三：生成 PRD 文档

将上述讨论结果汇总为一个 Markdown 文档，作为后续设计和开发的“唯一真实来源” (Source of Truth)。

- **推荐位置**：`docs/requirements.md` 或 `docs/features/<feature-name>.md`。
- **内容结构**：
    1.  背景与目标。
    2.  用户故事列表。
    3.  详细功能规格 (Specs)。
    4.  验收标准 (AC)。
    5.  待办事项清单 (Checklist)。

## Agent 交互协议

### 主动提问策略

Agent 不应一次性抛出 20 个问题。应采用**“草案-修正”**策略：

1.  根据用户模糊的指令，**快速起草**一份 `requirements.md` 草稿。
2.  在草稿中用 `[TODO]` 或 `[?]` 标记不确定的地方。
3.  询问用户：“我起草了一份需求文档，请确认其中的 `[?]` 部分是否符合你的预期？”

### 变更管理

- 如果在后续的 `Design` 或 `Impl` 阶段发现需求无法实现或需要变更，Agent **必须**返回此阶段。
- 更新 `docs/requirements.md`。
- 如果变更是重大的，必须追加一条新的 ADR 记录。

## 示例输出

**用户输入**：
> “帮我加一个用户积分功能。”

**Agent 响应 (Analysis Phase)**：
> “为了确保功能符合预期，我起草了以下需求简报，请确认：
>
> **1. 积分获取规则 [?]**
> - 目前假设：每日登录 +10 分，发帖 +5 分。是否有上限？
>
> **2. 积分消耗场景 [?]**
> - 目前假设：仅用于展示等级。是否需要兑换商品？
>
> **3. 数据一致性要求**
> - 决策：由于涉及资产，建议使用数据库事务，并记录完整的积分流水日志 (Audit Log)。
>
> 请确认上述规则，我将更新到 `docs/features/points_system.md`。”
